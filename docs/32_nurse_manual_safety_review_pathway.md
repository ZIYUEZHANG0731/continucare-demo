# 护士全量人工安全复核 Pathway

> 版本：0.1.0
> 状态：Streamlit 改造实施基线
> 适用范围：当前合成数据比赛原型
> 临床状态：未完成目标医院临床审批，不提供自动分级、预警、诊断、治疗或用药建议

## 1. 冻结结论

护士端从“例行记录一致性核对”调整为“患者确认记录的全量人工安全复核台”。

核心原则：

1. 每份满足准入条件的患者确认记录均创建护士复核 Task，系统不依据患者数值、症状、文本或趋势选择任务。
2. 系统只通知“有一份新记录待人工复核”，不通知“患者异常”或“患者高风险”。
3. 护士查看患者原话、结构化事实、数据来源和历史原始值，依据目标医院批准的护理规范自主判断。
4. 只有护士明确操作后，系统才记录“本次未上报”“需要补充核实”或“上报医生评估”。
5. 护士的判断属于人工工作流事实，不改变系统临床评估 `not_assessed`，也不生成自动 L0–L4 或 Alert。
6. 医生负责最终临床判断；护士上报不等于诊断、风险结论或处置建议。
7. 当前原型不真实发送消息、不连接急救通道、不写回正式病历。

一句话定位：

> 系统负责完整采集、可靠通知和责任留痕；护士负责人工安全复核和决定是否上报；医生负责临床判断。

## 2. 角色与责任

### 2.1 患者

- 完成 Pathway 规定的问卷或补充上报。
- 确认患者原话和结构化候选是否表达了本意。
- 对需要补充的问题继续提供信息。
- 不通过本系统等待急救响应；患者端始终显示固定的非急救通道说明。

### 2.2 系统

系统负责：

- 保存患者确认的 QuestionnaireResponse、Observation、原话和来源关系。
- 对每一份通过准入门的患者确认记录无条件创建护士 Task。
- 通知护士“新记录待复核”。
- 展示原始事实、缺失、冲突、单位、时间窗和数据来源。
- 保存护士接手、核实、联系、上报、完成和停止处理的记录。
- 护士上报后创建医生 Task，并通知医生“护士已人工上报一份记录”。
- 保存任务送达、接手、处理和医生确认状态。
- 根据任务创建时间进行运营超时提醒。

系统不负责：

- 根据数值、文本、症状或趋势判断异常。
- 设置或执行呕吐次数、液体摄入量、体重变化等临床阈值。
- 自动标红临床数据、生成风险等级或决定是否上报。
- 诊断、治疗、改药、停药或给出个体化就医建议。
- 把 `not_assessed`、护士未上报或任务完成解释为安全、低风险或病情稳定。

### 2.3 护士

- 接手属于本人或本科室的人工安全复核 Task。
- 核对患者原话、患者确认结果、结构化事实、时间窗和数据完整性。
- 依据目标医院批准的护理复核清单进行人工判断。
- 必要时联系患者并记录联系结果。
- 决定本次是否需要医生进行临床评估。
- 选择证据并填写明确原因后上报医生。
- 对错误任务进行取消或标记记录错误，并保留原因。

护士不负责：

- 代替医生诊断或决定治疗方案。
- 依据产品团队自行编写的阈值开展临床分级。
- 把个人判断包装成系统自动预警。

### 2.4 医生

- 接收护士人工上报的医生 Task。
- 查看患者确认事实、患者原话、护士核实记录和精确证据来源。
- 做最终临床判断，并记录已查看、需要继续补充或已完成评估。
- 决定是否进入医院既有诊疗、急症或病历流程。

## 3. Pathway 总览

```text
医生启动已版本锁定的随访 Pathway
→ 患者完成随访或补充上报
→ 患者明确确认
→ 系统保存完整患者记录和证据链
→ 系统无条件创建“护士人工安全复核”Task
→ 通知护士有新记录待复核
→ 护士接手
→ 护士开始复核
→ 护士查看原话、结构化事实、数据质量和历史原始值
→ 护士依据院内护理规范人工选择：
   ├─ A. 本次复核完成，未上报医生
   ├─ B. 需要联系患者补充核实
   ├─ C. 上报医生评估
   └─ D. 人工启动医院紧急流程（目标态；当前原型仅记录，不真实外发）
→ 所有动作写入 Task 历史、Provenance、Timeline 和 AuditEvent
→ 医生复诊速览只陈述患者事实和人工动作，不生成临床结论
```

## 4. 准入条件

系统只在以下条件全部满足时创建护士安全复核 Task：

1. 患者身份属于当前 Care Session。
2. QuestionnaireResponse 为 `completed`。
3. 患者已经对本轮表达作出明确确认。
4. QuestionnaireResponse、患者原话和最终来源已持久化。
5. 已生成的 Observation 必须为 `final` 且正确 `derivedFrom` 当前 QuestionnaireResponse。
6. 没有安全术语可映射时，允许 Observation 数量为 0，但患者确认原话必须保留。
7. 同一患者、同一提交、同一复核类型只能存在一个当前 Task。

准入失败时：

- 不推测患者风险。
- 不创建内容不完整的护士业务 Task。
- 创建数据完整性故障或只读提示，交由系统运维处理。
- 保留已经成功写入的原始患者证据，不补造资源。

## 5. 任务类型

### 5.1 护士安全复核 Task

建议业务编码：`manual-safety-review`。

触发方式：每份患者确认记录无条件触发，不读取临床值决定是否触发。

必须引用：

- Patient；
- Care Session；
- QuestionnaireResponse 精确版本；
- 所有可用 Observation 精确版本；
- 患者确认决定；
- Pathway 代码和版本；
- 护士责任角色。

不得引用为触发依据：

- 未获批准的 ClinicalRule；
- 自动风险等级；
- 模型生成的诊断、风险或处置建议。

### 5.2 患者补充核实子任务

当护士选择“需要补充核实”时创建或转换为等待患者的子流程。

必须包含：

- 护士希望核实的具体问题；
- 对应的患者原话或事实引用；
- 联系渠道或模拟渠道；
- 联系尝试和时间；
- 当前状态：待联系、等待患者、已收到补充、联系不上。

当前原型不真实发送，Communication 保持 `preparation`，页面明确标记“模拟，未真实发送”。

### 5.3 医生评估 Task

建议业务编码：`nurse-requested-doctor-review`。

只能由护士明确点击“上报医生评估”产生，不能由患者数据或模型自动产生。

必须包含：

- 上报护士；
- 上报时间；
- 上报原因；
- 护士选中的原始证据；
- 已进行的患者核实；
- 护士希望医生判断的问题；
- 当前患者是否仍在等待回复；
- 来源标记：`human-initiated`。

医生 Task 不包含系统生成的风险等级。其默认表述为：

> 护士已人工复核并请求医生查看；系统未进行临床风险分级。

## 6. 护士 Task 状态机

```text
requested（待接手）
→ received（已接手，已确定责任护士）
→ in-progress（正在人工复核）
   ├─ on-hold / waiting-patient（等待患者补充）
   │  → in-progress（收到补充，继续复核）
   ├─ completed / reviewed-no-escalation（完成，本次未上报）
   ├─ completed / escalated-to-doctor（已上报医生）
   ├─ completed / emergency-process-started（人工启动紧急流程）
   ├─ failed / unable-to-contact（按院内流程完成联系尝试但未联系上）
   ├─ cancelled（任务被明确取消）
   └─ entered-in-error（任务不应存在或记录错误）
```

状态语义：

- `reviewed-no-escalation` 只表示护士本次没有上报，不表示患者安全或低风险。
- `escalated-to-doctor` 只表示人工交接发生，不表示已经形成诊断或处置。
- `completed` 不等于临床闭环；医生 Task 和外部医院流程拥有独立状态。
- 每次状态变化都生成新版本，历史版本不得覆盖或删除。

## 7. 护士人工复核步骤

### Step 1：接手任务

页面显示：

- 患者；
- 提交时间；
- Pathway 名称和版本；
- 记录类型：定时随访或患者补充上报；
- 当前责任人；
- 运营处理时限；
- “系统未判断异常”的固定边界。

护士动作：`接手任务`。

系统写入：

- Task 新版本；
- owner；
- actor；
- 接手时间；
- Provenance；
- AuditEvent。

### Step 2：开始人工安全复核

页面按照 Pathway 字段顺序展示：

1. 患者原话；
2. 患者确认的最终表述；
3. 恶心是否存在；
4. 患者自选的恶心程度；
5. 过去24小时呕吐次数；
6. 过去24小时估计液体摄入量；
7. 当前是否腹痛；
8. 其他补充信息；
9. 原始回答、标准化 Observation 和来源关系；
10. 过去记录的原始数值和时间，不显示“变好/变坏/高风险”。

数据展示规则：

- 不依据数值使用临床红、黄、绿颜色。
- 可以标记缺失、单位不合法、时间窗不明、患者未确认、证据冲突等数据质量问题。
- 患者自己选择“严重”时原样展示“患者自报：严重”，不得改写为“系统判定严重”。
- 不把 Observation 缺失解释为患者没有症状。
- 不把护士上一轮未上报解释为本轮无需复核。

护士动作：`开始复核`。

### Step 3：完成医院护理复核清单

当前合成原型可以先展示不含临床阈值的固定检查维度：

- 已核对患者原话和患者确认结果；
- 已核对中文回答与患者原话是否一致；
- 已核对时间窗、单位、缺失和冲突；
- 已查看患者补充说明；
- 已决定是否需要联系患者补充；
- 已决定是否需要医生进行临床评估。

生产版本的临床问题、定量阈值和上报标准必须来自目标医院批准的护理规范，并保留：

- 协议 ID 和版本；
- 适用科室、药物、人群和场景；
- 审批人和审批时间；
- 生效和停用时间；
- 上报对象和响应流程；
- 回退方案。

软件只展示清单和保存护士勾选，不执行清单条件。

### Step 4A：本次复核完成，未上报医生

护士必须：

- 勾选完成复核声明；
- 填写或确认简短处理说明；
- 明确点击“完成本次复核”。

系统保存：

- `human_review_disposition=reviewed_no_escalation`；
- 护士说明；
- 精确证据摘要；
- 完成时间、actor、Provenance 和 AuditEvent。

页面固定提示：

> 本次未上报仅代表护士的本次人工工作流决定，不代表系统或护士已经证明患者安全、低风险或无需后续医疗评估。

### Step 4B：需要联系患者补充核实

护士必须填写：

- 需要核实的问题；
- 对应证据；
- 联系说明；
- 是否等待患者回复。

系统动作：

- Task 转入 `on-hold / waiting-patient`；
- 生成待人工核对的 Communication 草稿；
- 当前原型不发送；
- 保存联系尝试和沟通状态；
- 患者补充后回到 `in-progress`。

不得把“需要补充”直接标记为已完成。

### Step 4C：上报医生评估

护士必须填写：

- 上报原因；
- 选择至少一条患者原话、QuestionnaireResponse 或 Observation 作为证据；
- 已核实的事实；
- 希望医生判断的问题；
- 是否已经联系患者。

护士明确点击：`确认上报医生`。

系统原子完成：

1. 保存护士人工判断；
2. 完成护士 Task，结果为 `escalated-to-doctor`；
3. 创建唯一医生评估 Task；
4. 将护士选择的精确证据绑定到医生 Task；
5. 记录 `human-initiated`；
6. 创建通知投影；
7. 写入 Provenance、Timeline 和 AuditEvent。

任何一步失败则全部回滚，不能出现“护士端显示已上报，但医生没有任务”的状态。

### Step 4D：人工启动医院紧急流程

这是目标态能力，当前合成原型只能记录演示动作，不得声称已通知真实值班人员或急救系统。

生产启用前必须具备：

- 医院批准的急症 SOP；
- 真实身份与值班责任映射；
- 可靠通知和送达回执；
- 失败重试、替补和人工电话兜底；
- 明确的患者端固定急救说明；
- 演练和临床验收。

## 8. 医生接手 Pathway

当护士上报后，医生端新增“护士人工上报”队列，不与自动 Alert 混合。

医生首先看到：

- “来源：护士人工上报”；
- “系统临床评估：not_assessed”；
- 患者原话；
- 患者确认事实；
- 护士核实记录；
- 上报原因；
- 护士选择的精确证据；
- 患者是否仍在等待回复；
- 上报和送达时间。

医生可执行：

- 确认收到；
- 标记已查看；
- 请求护士或患者继续补充；
- 记录已进入院内既有临床流程；
- 完成医生 Task。

医生端不得把护士上报自动转换成诊断或治疗文字。

## 9. 通知策略

### 9.1 允许的通知

- 新患者确认记录待护士复核；
- 护士 Task 长时间无人接手；
- 护士正在等待患者补充；
- 护士已人工上报医生；
- 医生 Task 长时间无人接手；
- 消息送达失败或状态未知。

这些通知由任务状态和时间触发，不读取患者临床值。

### 9.2 禁止的通知

- “饮水量过低”；
- “呕吐次数异常”；
- “疑似脱水”；
- “高风险患者”；
- “病情恶化”；
- 任何未经医院批准且由系统计算的临床判断。

### 9.3 运营时限

可以配置“新记录在多少时间内应被护士查看”，但必须标记为运营处理时限，不是临床风险阈值。

当前版本不硬编码具体小时数。目标医院未配置时，页面显示“处理时限待医院配置”，不得默认为24小时。

## 10. Streamlit 信息架构

### 10.1 页面标题

主标题：`护士安全复核台`

副标题：

> 每份患者确认记录均由护士人工复核；系统不按数值判断异常，也不生成临床预警。

### 10.2 顶部概况

- 待接手；
- 复核中；
- 等待患者；
- 已上报医生；
- 今日完成；
- 运营超时。

所有数字来自 Task 状态，不来自风险等级。

### 10.3 左侧队列

Tabs：

1. 待接手；
2. 复核中；
3. 等待患者；
4. 已上报；
5. 已完成。

任务卡显示：

- 患者；
- Pathway；
- 记录类型；
- 提交时间；
- 当前状态；
- 当前责任人；
- 运营处理时限状态。

任务卡不显示自动风险颜色、L0–L4或系统异常标签。

### 10.4 中部患者记录

按 Pathway 顺序展示字段，同时提供：

- 查看患者原话；
- 查看患者确认记录；
- 查看结构化事实；
- 查看历史原始值；
- 查看证据链；
- 查看数据质量问题。

数据质量问题使用中性标签，例如“缺少时间窗”“单位无法验证”“原话未安全映射”，不能使用“危险”或“高风险”。

### 10.5 右侧人工操作区

根据状态只显示当前允许动作：

- 接手任务；
- 开始复核；
- 联系患者补充；
- 完成本次复核；
- 上报医生评估；
- 取消任务；
- 标记记录错误。

“上报医生评估”使用独立确认区域，必须完成必填项后才可点击。

### 10.6 已处理详情

显示：

- 护士人工处理结果；
- 处理说明；
- 是否联系患者；
- 是否上报医生；
- 医生 Task 状态；
- 完整动作历史；
- 精确证据引用；
- “临床评估仍为 not_assessed”边界。

## 11. 数据与审计合同

护士处理结果建议使用受控字段：

```text
human_review_disposition:
  - reviewed_no_escalation
  - clarification_required
  - escalated_to_doctor
  - emergency_process_started
  - unable_to_contact
  - cancelled
  - entered_in_error
```

禁止使用：

```text
safe
low_risk
high_risk
dehydrated
pancreatitis_suspected
treatment_needed
```

每个动作至少保存：

- actor FHIR reference；
- Task ID 和版本；
- 患者和 Pathway；
- 动作；
- 非空说明；
- 带时区时间；
- 输入证据精确版本；
- 前后状态；
- Provenance；
- AuditEvent；
- 是否发生外部发送及送达状态。

关键审计事件建议：

- `manual_safety_review_task_created`；
- `manual_safety_review_claimed`；
- `manual_safety_review_started`；
- `manual_safety_review_clarification_requested`；
- `manual_safety_review_resumed`；
- `manual_safety_review_completed_without_escalation`；
- `manual_safety_review_escalated_to_doctor`；
- `doctor_review_task_created_from_nurse`；
- `doctor_review_task_acknowledged`；
- `doctor_review_task_completed`；
- `manual_safety_review_cancelled`；
- `manual_safety_review_entered_in_error`。

## 12. 故障与兜底

### 12.1 Task 创建失败

- 患者记录不得丢失或回滚成未确认。
- 页面明确显示“患者记录已保存，但人工复核任务创建失败”。
- 创建运维故障，禁止伪装为护士已收到。
- 支持幂等重建同一个 Task。

### 12.2 通知失败

- Task 保持待接手。
- 保存通知失败或未知状态。
- 进入运营故障队列。
- 不把“已创建通知内容”当作“已送达”。

### 12.3 无护士接手

- 只根据运营处理时限通知护士长或管理员。
- 不根据患者数值升级临床风险。
- 页面持续显示未接手时长和责任归属。

### 12.4 医生 Task 创建失败

- 护士“确认上报”事务整体失败。
- 护士 Task 保持复核中。
- 页面提示上报尚未完成，允许安全重试。
- 不产生虚假的“医生已收到”。

### 12.5 并发和旧页面

- 每次操作比较 story generation 和 Task 当前版本。
- 旧标签页不得覆盖新动作。
- 重复完全相同的动作幂等。
- 不同说明、不同责任人或不同目标状态的重复提交必须冲突并要求刷新。

## 13. Demo 主故事

为了证明护士角色，应演示“人工判断和责任交接”，而不是让系统自动触发异常。

建议故事：

1. 医生启动合成 GLP‑1 随访 Pathway。
2. 合成患者提交并确认一组患者自报事实。
3. 系统保存事实并无条件创建护士安全复核 Task。
4. 页面明确显示：系统没有阈值、没有 Alert、临床评估为 `not_assessed`。
5. 护士接手并查看原话、结构化事实和证据链。
6. 演示者以护士身份人工选择“上报医生评估”，填写原因并选择证据。
7. 系统创建医生 Task，显示来源为护士人工上报。
8. 医生确认收到并查看证据，仍不生成自动诊断或治疗建议。
9. 审计页回放患者确认、护士判断、上报和医生接手。

演示必须明确：

- 护士选择是合成场景中的人工动作，不是系统根据患者数据推荐。
- 当前没有真实医院护理阈值、真实通知或临床验证。
- `not_assessed` 不表示安全。

## 14. Streamlit 实施顺序

### Slice 1：护士全量人工复核主流程

- 保持患者确认后无条件创建 manual review Task。
- 页面改名和边界文案。
- 按 Pathway 顺序展示全部患者确认事实。
- 新增人工复核清单。
- 将结果改为“本次未上报 / 需要补充 / 上报医生”。

### Slice 2：补充核实分支

- `waiting-patient` 状态；
- 联系问题和联系记录；
- 待核对 Communication；
- 收到患者补充后恢复复核。

### Slice 3：护士上报医生

- 新增护士人工上报表单；
- 创建医生 Task；
- 原子交接；
- 医生端上报队列和接手动作；
- 审计回放。

### Slice 4：运营可靠性

- 处理时限配置；
- 未接手和通知失败队列；
- 送达状态；
- 责任人替补；
- 管理端指标。

### Slice 5：目标医院协议接入

- 只读护理规范版本；
- 科室、产品和人群范围；
- 审批记录；
- 真实身份、权限、通知和演练。

任何 Slice 都不得静默增加临床阈值、风险等级或自动 Alert。

## 15. 验收标准

### 15.1 正向验收

- 每份患者确认记录恰好创建一个护士安全复核 Task。
- Task 创建不依赖患者具体数值或症状。
- 护士能查看患者原话、结构化事实、来源和历史原始值。
- 护士能完成人工复核并明确记录本次未上报。
- 护士能发起补充核实，任务进入等待患者而不是直接完成。
- 护士能选择证据并上报医生。
- 上报后医生端出现唯一 Task，并明确来源为护士人工判断。
- 全部动作具有 Task 版本、Provenance 和 AuditEvent。

### 15.2 安全验收

- `clinical_rules=[]`。
- `evaluate_risk()` 继续返回 `not_assessed / create_alert=false`。
- 患者数值变化不会自动改变任务优先级、颜色、分支或通知对象。
- 页面不出现系统生成的“异常、高风险、恶化、脱水、疑似诊断”。
- “护士本次未上报”不会被表述为安全或低风险。
- 护士上报失败时医生端不会出现半个 Task，护士端也不会显示成功。
- 当前原型不会产生真实发送或外部写入。

### 15.3 回归验收

- 患者确认门不能绕过。
- QuestionnaireResponse、Observation 和 `derivedFrom` 保持正确。
- Summary 只陈述患者确认事实和人工动作。
- 当前 Clinical Memory、审计链和并发 generation 护栏保持有效。
- 用户现有数据和历史 Task 仍能只读展示，不被迁移脚本覆盖或删除。

## 16. 本 Pathway 不解决的事项

- 不提供目标医院的具体上报阈值。
- 不证明护士人工判断的临床有效性。
- 不替代医院护理制度、值班制度或急症流程。
- 不声明产品已经完成医疗器械分类、注册或真实临床部署评估。
- 不启用真实患者、真实消息、真实医生任务或正式病历写回。
