### 一屏看懂 ContinuCare

患者真正生活的几十天发生在医院之外。ContinuCare 不试图让 AI 替医生做判断，而是帮助医疗团队恢复这段长期缺失的上下文：医生先确认随访方案，患者按路径完成记录，AI 将自由表达整理为待确认候选，患者确认后生成可追溯的结构化事实；护士对每份确认记录进行人工安全复核，必要时上报医生；医生在复诊前看到的是有来源、有版本、有责任记录的连续上下文，而不是一段无法核验的 AI 总结。

> **核心主张：AI 负责理解和组织，系统负责证明，患者和医护负责决定。**

## 二、方案成果展示

### 2.1 命题场景：医院看得到离院和复诊，却看不到中间几十天

一次门诊或出院只占患者生活中的极短时间。症状、饮食、依从、担忧、缺失记录和医护沟通，大多发生在院外。现有流程常依赖电话、聊天记录和患者复诊时的回忆，形成三个连续断点：

1. **照护断线**：人工随访量大、节奏不统一，患者变化不能稳定进入团队工作流。
2. **事实断线**：患者原话、表单答案、护士记录和医生判断分散在不同载体，难以形成可修订、可回放的纵向记录。
3. **责任断线**：即使发现需要关注的信息，也缺少“谁接手、核对了什么、是否上报、医生是否查看”的完整责任链。

结果是：医生在复诊前仍面对碎片，护士重复整理，患者重复讲述；AI 即使能生成一段流畅文字，也很难回答“这句话来自哪里、当时谁确认过、之后谁处理过”。

### 2.2 我们的关键洞察

行业并不缺“再做一次随访”的工具，也不缺“让模型写一段摘要”的能力。真正的断层是：患者离院后的表达没有被沉淀成一种可由患者确认、可由护士接手、可由医生复用、可从结论回到证据的长期事实系统。

因此，ContinuCare 的最终产品结果不是一段 AI 回复，而是医生可以快速审阅的一组连续上下文：

- 患者报告了什么，何时发生；
- 哪些内容是患者明确确认的；
- 哪些事实来自结构化问卷，哪些来自自然语言补充；
- 护士是否核对、联系或上报；
- 数据是否缺失、迟到、修订或冲突；
- 每条摘要和图表数据点能否回到原始记录。

### 2.3 方案优势与创新点

#### 创新一：从“AI回答”转向“证据化连续记忆”

患者原话不会被摘要覆盖。系统保存原始回答、患者确认、QuestionnaireResponse、Observation、医护 Task、Provenance 和审计事件；医生看到的事实均带证据引用。Clinical Memory 不是聊天记录的再次总结，而是按临床有效时间组织、保留版本与修订关系的纵向事实层。

#### 创新二：AI进入核心链路，但不能越过事实门

豆包 Doubao-Seed-2.0-lite 可参与语义候选抽取、Safety Critic、患者语言改写和受控 Summary 编排。但模型不能直接创建临床事实、风险等级、医护决定或患者确认。模型不可用时，系统回退本地确定性逻辑，人工确认门仍然存在。

#### 创新三：三端不是三个页面，而是一条责任接力链

医生确认方案后才能开启随访；患者确认后才形成最终事实并进入护士任务；护士明确上报后才进入医生“护理协作”待办。三端共享同一个版本化事实库，进度从持久化事实恢复，不依赖浏览器临时状态。

#### 创新四：把“医疗谨慎”做成可运行的产品能力

在没有目标医院批准的临床规则时，系统明确返回 `not_assessed`，不把“未评估”解释为低风险或安全。每份患者确认记录进入护士人工安全复核，由护士依据医院规范决定是否上报，医生负责最终临床判断。

#### 创新五：从单病种原型走向可配置平台

当前以合成 GLP-1 随访为演示场景，但患者端由版本化 FHIR Questionnaire 动态驱动，问题、选项、条件显示和 Observation Mapping 不硬编码在界面中。未来扩展新病种主要依靠发布新的 Pathway、Questionnaire、术语和知识版本，而不是复制一套应用。

### 2.4 Before / After

| Before | After |
| --- | --- |
| 院外信息停留在电话、聊天或患者回忆中 | 患者确认后沉淀为可追溯的结构化记录 |
| AI生成文本难以证明来源 | 每项内容绑定患者原话、FHIR资源和医护动作 |
| 患者、护士、医生各自使用孤立工具 | 三角色在同一事实链中接力 |

## 2.5 具体方案说明：完整五步照护闭环

### 第一步：医生确认随访方案

医生端基于合成 EHR 摘要和当前发布的知识版本，展示候选监测指标、频率、时间范围及证据来源。医生选择并确认后，服务端重新校验所有指标与版本，原子地开启患者随访；客户端不能注入未发布指标或绕过证据绑定。

**当前实现：**

- 独立医生端 React 工作台；
- 版本化随访方案与服务端重新校验；
- 六个受治理指标候选，包括体重、恶心、呕吐次数、液体摄入和腹痛；
- 合成演示模式，不读取真实病历；
- 不自动生成治疗或用药建议。

### 第二步：患者表达、AI整理、患者确认

患者端从当前锁定的 FHIR Questionnaire 动态渲染问题。患者可以使用结构化选项，也可以补充自然语言。AI读取的不是开放世界医疗问题，而是当前随访上下文中允许的受限任务：识别时间、主语、否定、数值、单位和已发布候选，并返回原文证据位置。

AI的输出先经过 Safety Critic 和本地硬规则；随后以“系统这样理解，是否符合你的本意”的形式展示给患者。只有患者明确确认后，才由确定性 FHIR Builder 保存完整 QuestionnaireResponse，并把安全映射的事实写为 final Observation。

![患者最终确认页面](../assets/screenshots/submission_patient_final_review_doubao.png)

*图 2：患者端最终确认。AI 只整理为待确认记录，患者确认后才进入长期事实层。*

### 第三步：FHIR事实与Clinical Memory沉淀

系统同时保存不同职责的数据层：

![FHIR 证据链：从医生结论逐层回到患者原话](../docs/assets/report-diagrams/03-fhir-evidence-chain.png)

*证据图 C：患者原话、FHIR 事实、Clinical Memory、人工任务与医生随访小结保持可追溯连接。*

- **QuestionnaireResponse**：保留患者实际回答与本轮问题版本；
- **Observation**：只由确定性代码构造，通过 `derivedFrom` 回到来源回答；
- **Clinical Memory**：按临床有效时间组织事实，处理迟到、修订、冲突和缺失；
- **State Snapshot**：表达 current、stale、unknown、conflict，不把缺失推断为正常；
- **Evidence Summary**：只组织已有事实与证据，不生成新的临床事实。

### 第四步：护士全量人工安全复核

每份满足准入条件的患者确认记录都会创建护士人工安全复核 Task。系统不读取具体症状或数值来决定“这位患者是否异常”，也不使用未经医院批准的临床阈值进行自动分级。

护士可以：

1. 接手任务；
2. 核对患者原话、确认内容、结构化事实、时间窗、单位和数据完整性；
3. 记录需要补充核实的问题；
4. 完成本次复核但不作临床安全结论；
5. 明确上报医生进行临床评估。

护士的决定作为人工工作流事实保存，不会改写系统的 `not_assessed` 状态。只有护士明确选择“上报医生评估”，医生端才出现护理协作待办。

![护士端人工安全复核队列](../assets/screenshots/submission_nurse_review_queue.png)

*图 3：当前 React 护士端展示 5 份患者确认记录、患者原话和结构化回答；是否补充或上报由护士人工决定。*

### 第五步：医生查看连续上下文与护理协作

医生端将本轮随访事实、近期指标、患者补充、护士动作和证据引用组合为可扫描的工作台。医生查看的不是一段不可解释的生成文字，而是可以逐项下钻的事实集合。

![医生端五日体重与症状趋势](../assets/screenshots/submission_doctor_trends.png)

*图 4：医生端展示 5 天体重与症状原始趋势；每个指标保留来源引用，趋势本身不构成临床判断。*

![医生端五日呕吐与液体摄入趋势](../assets/screenshots/submission_doctor_trends_lower.png)

*图 5：医生端继续展示呕吐次数、液体摄入与最新症状状态；数据点来自确定性事实服务。*

医生可以继续查看证据引用、历史版本和护理协作；真实医院版本再按审批接入 EMR、SSO 和正式临床工作流。

## 2.6 AI应用深度：受控 Agentic Clinical Workflow

ContinuCare 当前更准确的定义是“受控 Agentic Clinical Workflow”，而不是多个自治 Agent 自主协商。每个模型阶段只完成一个可验证任务；事实、状态和临床边界由确定性服务控制。

| 智能阶段 | AI负责 | AI不能做 | 失败时 |
| --- | --- | --- | --- |
| Care Agent | 从患者自由表达中提取受限候选、识别时间与证据位置 | 不能诊断、创建Observation或替患者确认 | 回退本地确定性语义解析或结构化问卷 |
| Safety Critic | 检查遗漏、越界、主语、否定、时间和证据一致性 | 不能推翻确定性硬规则，只能降级或触发定向补抽取 | 硬规则继续运行 |
| Language Rewriter | 在事实锁定条件下生成患者可读表达 | 不能改变数字、单位、症状、程度、肯否或时间 | 回退固定语言模板 |
| Controlled Summary | 对已有 fact ID 分组、排序 | 不能生成正文、风险、建议或新的事实 | 回退完整确定性事实清单 |

所有模型调用均记录模型、Prompt版本、请求ID、延迟、失败原因与回退路径；密钥不进入审计日志。当前默认使用火山方舟 OpenAI-compatible 接口与 `doubao-seed-2-0-lite-260215`，模型仅处理合成演示文本。

### 为什么这种设计仍然具有AI创新性

医疗场景中的AI深度不应只用“模型调用次数”衡量。ContinuCare 将AI放在最需要语义理解的关键位置，同时把每个输出限制为可验证合同：

- 语言理解结果必须带逐字证据；
- 新事实必须经过患者确认；
- 医护任务必须由业务条件或人工决定产生；
- 摘要必须覆盖既有事实，不能自由编造；
- 任何模型阶段失败都不能取消人工门或改变安全边界。

这使AI从“生成一段看似正确的内容”，转变为“在可追溯工作流中提出可核验候选”。

## 2.7 系统架构与鲁棒性

![ContinuCare 系统架构：确定性主链、受控 AI 辅助与全程治理](../docs/assets/report-diagrams/04-system-architecture-governance.png)

*架构图 D：确定性临床与工作流服务构成主链，受控 AI 仅承担辅助能力，患者确认、护士复核、医生判断与审计治理贯穿全程。*

**鲁棒性设计：**

- 主链不依赖外部服务才能安全完成；
- 写操作由服务端重新校验角色、状态和版本；
- 关键发布采用事务、幂等键与并发控制；
- 页面刷新后从SQLite事实恢复进度，不依赖浏览器session state；
- 外部业务适配器保持安全关闭，偶然存在凭据不会自动启用；
- Knowledge独立只读，不读取患者故事，也不授权运行时动作。

## 2.8 医疗安全：把边界做成系统行为，而不是免责声明

ContinuCare的安全边界不是只写在页脚，而是体现在每个关键写入点：

| 风险 | 系统控制 |
| --- | --- |
| AI误解患者表达 | 逐字证据、Safety Critic、术语与单位校验、患者确认 |
| 模型直接形成临床事实 | 禁止；FHIR资源只由确定性Builder创建 |
| 未获批准的自动风险判断 | 规则为空时fail-closed并显示`not_assessed` |
| “未上报”等于“患者安全” | 页面明确区分工作流决定与临床判断 |
| AI摘要遗漏或编造 | fact ID合同、mandatory覆盖、证据锁与确定性回退 |
| 外部发送误触发 | `SEND_ENABLED=False`，Communication保持preparation |
| 真实数据和凭据泄露 | 当前仅合成数据；凭据不进入日志、数据库或Git |
| 角色越权与旧页面写入 | 服务端角色边界、状态校验、版本和generation护栏 |

患者、护士和医生形成三个人工决定点：

1. 患者决定系统是否准确表达了本意；
2. 护士决定是否需要补充核实或上报医生；
3. 医生完成最终临床判断。

## 2.9 方案价值与可验证性

### 对医生

- 将院外事实、缺失、护理动作和患者问题提前组织；
- 减少复诊时从零拼接信息和重复追问；
- 任何摘要或图表可以下钻原始证据，不要求医生相信模型本身；
- 保留医生接受、修改或拒绝的权利。

### 对护士

- 将分散的患者记录转为可接手、可补充、可上报、可追踪的任务；
- 统一展示患者原话、确认事实、时间窗和数据质量；
- 记录责任人和每次状态变化；
- 避免产品团队在临床批准前擅自编写阈值。

### 对患者

- 用低负担方式按路径记录，不必在复诊时完全依靠回忆；
- 自由表达先由AI整理，再由本人确认；
- 明确知道系统记录了什么；
- 紧急情况固定提示联系急救或前往急诊，不等待AI回复。

### 对医院

- 获得可配置、可审计、可版本管理的院外照护基础设施；
- 可从单科室、单Pathway、只读旁路开始；
- FHIR契约和适配器降低后续系统集成成本；
- 用真实流程数据验证价值，而不是只看模型演示。

### 量化价值的验证方式

当前原型尚未进入真实医院试点，因此不虚构“节省50%时间”或“降低X%风险”。首期建议采用试点前后对照：

| 指标 | 计算方式 | 价值假设 |
| --- | --- | --- |
| 医生复诊准备时间 | 试点前后单患者准备时间中位数 | 连续上下文减少信息拼接时间 |
| 重复追问次数 | 每次复诊重复询问已记录问题数 | 证据化院外记录提高上下文复用 |
| Summary使用情况 | 打开率、审阅率、编辑率、主观帮助比例 | 验证医生是否真正使用成果 |
| 护士单份复核耗时 | 任务接手至完成的活跃处理时间 | 统一事实视图减少查找和整理 |
| 任务闭环时间 | requested至completed的时间分布 | 责任链使积压和超时可见 |
| 证据完整率 | 可回到原话和标准化记录的简报条目占比 | 验证可追溯性 |
| 安全越界率 | 预定义安全测试中未拦截越界输出占比 | 验证受控AI边界 |

价值计算示例：

```text
医生月度节省时间
= 月复诊患者数 ×（试点前单患者准备时间 - 使用后单患者准备时间）

护士月度节省时间
= 月随访记录数 ×（传统整理平均耗时 - 系统辅助复核平均耗时）
```

只有在获得真实基线和试点结果后，才填入改善比例。

## 2.11 可落地性与推广路径

### Phase A：比赛工程原型

- 单一合成GLP-1 Pathway；
- 患者、护士、医生三端闭环；
- 受控AI语义链；
- FHIR事实、证据、版本和审计；
- 本地可回放演示；
- 不使用真实患者数据，不连接生产系统。

### Phase B：单科室旁路试点

- 选择一个科室、一条Pathway和明确目标人群；
- 只读导入基础信息，不写回EMR；
- 与科室共同批准问卷、术语、护理清单和角色责任；
- 先在影子模式验证记录完整性和工作流影响；
- 记录医生、护士、患者和安全指标，不预设改善数字。

### Phase C：医院工作流集成

- SSO、组织权限、审计和患者授权；
- FHIR/EMR接口和正式Profile；
- 飞书/Aily测试租户验证、消息回调与送达状态；
- Pathway审批、版本发布和回滚；
- 经临床批准后验证规则和人工响应流程。

### Phase D：可复制平台

- 多科室Pathway Library；
- 高血压、术后恢复等新场景；
- 多医院部署、监控与质控；
- 按科室、患者随访量或实施服务形成商业模式。

推广的最小单元不是一套重新开发的软件，而是“Pathway + Questionnaire + Observation Mapping + 护理工作流 + Summary视图”的版本化组合。

## 四、附录

### 4.1 当前能力边界声明

1. 当前是仅使用合成数据的本地Web工程原型，不是临床试点或生产系统。
2. 系统不是医疗急救通道，不提供诊断、治疗、自动分诊或用药建议。
3. 当前无获批临床规则，不自动生成L0–L4、Alert或处置建议。
4. 护士上报是人工工作流动作，不等于诊断或风险结论。
5. Knowledge资料只提供信息和治理证据，不直接授权运行时动作。
6. 飞书用于企业导师和团队沟通；产品侧飞书 Bot、Aily 与 Bitable 尚未接入真实临床工作流。
7. 豆包工程评测和自动化测试不代表临床有效性。
8. 真实患者使用前仍需伦理、法务、隐私、信息安全、临床与术语审批。

## 结语

我们不让AI替代医生，而是让AI帮助医疗团队找回患者离院后的上下文。

ContinuCare希望把每一次患者表达，转化为一条可以被本人确认、被护士接手、被医生审阅、被系统证明的连续记录。先把真实事实和责任链连接起来，再在临床批准和真实验证的前提下逐步增加自动化，这是一条更谨慎，也更可能进入医院实际工作流的AI路径。

> **ContinuCare Copilot：让院外变化不再消失，让医生在复诊前看见一段可信的连续故事。**
